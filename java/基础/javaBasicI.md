## Java 编译 & 解释

### 编译

 .java ==编译器==> .class

### 解释

 .class ==解释器==> 机器语言执行


### AOT : Ahead Of Time Compilation 提前编译

JDK9 中引入

与之对应的是 JIT Just In Time Compilation 及时编译

传统的 JIT 会在真正运行 .java 文件时才通过编译器转成 .class，然后再由解释器慢慢解释成机器码运行，在这个过程中需要 JVM JRE 等支持

而 AOT 则在项目打包时，自动直接将 .java 文件编译成机器码

AOT VS JIT：

| 对比维度 | JIT（即时编译） | AOT（提前编译） |
|---------|------------|-----------|
| 编译时机 | 运行时编译 | 运行前编译 |
| 启动速度 | 较慢（需要预热） | 快（无需预热） |
| 峰值性能 | 更高（运行时优化） | 较低（缺少运行时信息） |
| 内存占用 | 较高 | 较低 |
| 打包体积 | 较小 | 较大（包含机器码） |
| 动态特性支持 | 完全支持 | 受限（反射、动态代理等） |
| 适用场景 | 长时间运行的服务 | 云原生、Serverless、CLI 工具 |


#### AOT 为什么不支持动态特性

因为 java 的动态本质是由 JVM 支持的， AOT 直接将 .java 编译成机器码，运行时完全不需要 JVM 或者其他库，CPU可以直接运行，那么这就丢失了 JVM 的动态支持

## 包装类 & 基础类型

### 基本类型的本质

即地址的别名

比如基本类型 type name = value; 值 value 存在内存中（不能直接确定在栈还是堆），地址是 0x00012；那么基本类型变量 name 本质就是地址 0x00012，


### Integer 缓存机制

直接用 Integer.valueOf(int) 方法创建的对象，如果数值在 [-128, 127] 的区间内，得到的总会是一个已有的缓存的对象；自动装箱时，Integer i = 10，与 Integer i = Integer.valueOf(10) 同等

但是使用 new 创建区间内对象时，由于使用了 new，所以得到的会是一个刚刚创建的新对象
