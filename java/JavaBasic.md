## Java 编译 & 解释

### 编译

.java ==编译器==> .class

### 解释

.class ==解释器==> 机器语言

机器语言可以直接由 CPU 执行（计组知识）


### AOT : Ahead Of Time Compilation 提前编译

在 JDK9 中引入。

与之对应的是 `JIT` Just In Time Compilation 即时编译。JIT 会在真正运行项目时，才通过编译器将项目文件转成字节码，然后再由解释器解释成机器码，最后由 CPU 运行。在这个过程中需要 `javac` 和 `JVM` 支持，解释器包含于 JVM 中。

而 AOT 则在项目打包时直接将 .java 文件编译成机器码。然而，这并非表明 AOT 不需要 javac，相反， AOT 的前期工作中仍然需要使用 javac 转字节码，在此之后则完全不需要 JVM 

AOT VS JIT：

|  | JIT（即时编译） | AOT（提前编译） |
|---------|------------|-----------|
| 编译时机 | 运行时编译 | 运行前编译 |
| 启动速度 | 较慢（需要预热） | 快（无需预热） |
| 峰值性能 | 更高（运行时优化） | 较低（缺少运行时信息） |
| 内存占用 | 较高 | 较低 |
| 打包体积 | 较小 | 较大（包含机器码） |
| 动态特性支持 | 完全支持 | 受限（反射、动态代理等） |
| 适用场景 | 长时间运行的服务 | 云原生、Serverless、CLI 工具 |


#### AOT 为什么不支持动态特性

我们知道 Java 的动态特性本质是由 JVM 支持的，JIT 方式在使用 javac 将 .java 编译成 .class 字节码后，还需要 JVM 对字节码进行解释运行，而这个过程中就有运行的 JVM 可以支持动态特性。

而 AOT 直接将 .java 编译成机器码，运行时完全不需要 JVM 支持，而是直接让 CPU 运行，那么这就丢失了 JVM 的动态支持

## 变量-基础知识

### 基本类型

#### 基本类型的本质

本质即为地址的别名

比如基本类型 `type name = value;` 值 value 存在内存中（不能直接确定在栈还是堆），地址是 0x00012；那么基本类型变量 name 本质就是地址 0x00012，在编译阶段，变量 name 这个名字会被完全删除，字节码中存在的则是一串地址 0x00012 取而代之。

#### 基本类型变量存在哪？

基本类型变量要分局部变量和全局变量。

- `局部变量` 例如方法内部、代码块内定义的基本类型变量，存在于 `栈/局部变量表` 内；

- `全局变量` 例如实例化对象的成员变量、static 变量就存在 `堆` 中。


### 类与对象

#### 对象的本质

对象需要看成三部分：`对象名称`、`对象结构`和`对象数据`。

- `对象名称`本质上是一个存储对象数据在内存中位置的 `指针` 变量，指向对象所在的内存地址，这与基本变量类型变量本质`地址别名`区分开来。

- `对象结构`规定了这个对象的类中包含哪些成员。

- `对象数据`存的是这个对象的成员的值。

不过从严格上讲，Java官方极力避免使用`指针`这个源自于 C 的术语，而是将其称为`引用`。

>那么为什么官方极力避免使用指针这个名称？原因有三：

- C/Cpp 中的指针指向的是一个固定的地址，这意味着如果不进行人为干预，指针永远指向固定的地址。而在 Java 中，由于存在垃圾回收机制，对象的地址是不固定的，一个地址在 0x111002 的对象，在一轮 GC 后地址就被 JVM 动态修改到了 0x233380，这是开发者不能控制的。所以实际上不能将对象看成指向地址的指针。

- Java 中不存在指针运算，比如指针自增、指针加减法等，原因仍然是 Java 垃圾回收机制，内存中数据的位置是动态调整的而非不变，所以指针运算几乎不能保证结果与开发者想法一致，所以官方禁止了在 Java 中使用指针运算。

- Java 中的引用的底层实现方式并没有写死，不同的 JVM 有不同的实现方式；而指针在 C/Cpp 中的实现方式是严格固定的。

#### 对象存在哪？

对象变量首先要分成`对象名称`、`对象结构`和`对象数据`，同时也要分全局和局部。

- `对象结构`不管是全局还是局部，从 Java8 开始，统一存在`元空间`内，而非`栈`或者`堆`。

- `对象名称`的话需要分成全局和局部：当全局时，存在`堆`；局部时，存在`栈`。

- `对象数据`同样需要分成全局和局部：全局时，存在`堆`；局部时，则需要判断是否发生了`对象逃逸`。

> 对象逃逸是什么？ 

这是 Java7 引入的一种内存优化方式，主要分析一个方法内实例化的局部对象变量，其生命周期是否超出了这个方法？比如，该对象作为方法返回值被 return；或者该对象被赋值给了全局变量，那么这个时候该对象理应存在于 `堆` 区。如果这个对象生命周期仅限于该方法内，方法结束后就应该释放，那么直接把这个对象存在`栈`内更方便，也更节省`堆`的空间。


### 基本类型的包装类

#### 包装类和基本类型

8种基本类型都有包装类，这是为了方便泛型和数据存储。

#### 包装类的缓存机制

`Byte` `Short` `Integer` `Long` 这四种整型类都有缓存机制，支持 [-128, 127] 的缓存。

缓存机制主要是为了配合`自动拆/装箱`，即直接使用基本类型变量来构建对象的行为。例如直接用 `Integer i = Integer.valueOf(10)` 或者 `Integer i = 10` 创建的对象，如果数值在 [-128, 127] 的区间内，得到的总会是一个已有的缓存的对象，使用`==`比较地址时，返回一定是`true`；而使用 `Integer i = new Integer(int)` 创建区间内对象时，由于使用了 new，所以得到的会是一个刚刚创建的新对象，肯定不会是缓存起来的那个实例对象。

另外，`Integer`的缓存上限 127 可以通过 JVM 参数自定义，下限则不可自定义。其他三种整型包装类也不能自定义上下限，这种方式也不被建议，容易造成 OOM。

#### 自动拆/装箱

装箱，本质是调用了`Type.valueOf(int)`方法；拆箱本质就是调用`obj.typeValue()`方法，例如

```java
Integer I = new Integer(10);
int a = I.intValue();
int b = I;
```

a 和 b 的创建本质是一样的。


### 成员变量和局部变量

||成员变量|局部变量|
|----|----|----|
|语法|可用public/private/static/final修饰|只可用final修饰|
|存储|堆|栈|
|生命周期|与对象相同|代码块内生存|
|默认值|定义如果没有显式赋值，自动赋予默认值|若无显式赋值，不会自动赋值|

一个一个说，成员变量被`static`修饰时，所有该类的实例共享同一个变量，调用时也使用类名调用；其他的`static`变量也一定要是全局的，这与局部变量明显冲突。

> 为什么成员变量要有默认值？

根本原因是因为编译器无法完全得知对象的成员变量什么时候创建、什么时候被使用，因为成员变量有可能在构造方法中赋值、有可能通过`setter`方法赋值、有可能是在多态中赋值的、有可能是在反射等场景、甚至有可能压根没有用等号赋值而是直接依赖注入了......这就造成了一个结果：成员变量这种长周期、大范围、多场景的变量，编译器根本无法得知其全部调用时机。而局部变量这种短周期小范围的变量，编译器一眼就可以看出何时赋值何时使用。

> 如果编译器无法阻止`成员变量未赋值之前就使用`的这种情况的话，会发生什么？

由于成员变量是跟着对象生命周期走的，对象创建之时，成员变量自然也分得了一部分空间。然而，这一部分空间也可能是其他被回收的空间，其空间存储的痕迹此时未被清理，如果这个时候贸然调用成员变量，其数值会完全无法预测，有可能是乱码，甚至有可能造成崩溃。

> 该怎么做？

为了防止这种不安全的使用，编译器会给未赋值的成员变量自动赋予默认值，一劳永逸。

#### static 静态变量

静态变量是`全局`的，所以基本上都是存在`堆`区的，程序运行期间也只会分配一次内存，因此`static`变量不能在方法内部声明，否则可能有`多次声明static变量`的风险。

如果类的成员变量是静态的，这个成员变量同样只会分配一次内存，并且全体类的实例访问该成员变量时，访问的都是同一片空间（不论是通过类名还是对象）。

> 那么类的静态成员变量存在什么地方？

我们知道，类的实例化在大多数情况下存在`堆`区，每次`new`一个新对象，都会分配一块新的内存，其普通的成员变量就存在这片内存中，通过该对象的名称才能够进行访问。

然而，静态成员变量需要让全体类的对象都能够访问得到，因此如果将其放在对象的空间下面，显然是不方便的，于是符合直觉地，`static`成员变量被放在一片公共区域：`类本身对应的Class对象内部`。

当类被调用时，首先会由`类加载器`实例化一个`java.lang.Class`对象（传入的参数就是这个类本身），而既然是对象，就会分配空间，自然就等效于这个类的公共空间，静态成员变量也就存在这个区域内，以便让所有类的实例化调用。

此外，在绝大多数场景下，这个类的Class类型对象在整个程序运行期间，都是同一个，因为用到的都是 JVM 默认的类加载器，同一个类加载器代表同一个命名空间。如果是不同的类加载器，比如你手动`new`了一个类加载器，然后加载这个类，那么内存中就会出现两个同一个类的Class对象，但实际上二者在 JVM 内部的命名不是同一个。

> 静态成员变量的生命周期。

出生：类加载，也即类被创建、被调用静态成员等。

死亡：类卸载，这需要满足三个条件：

- 所有类的实例对象全部被 GC；

- 这个类的类加载器被 GC；

- 这个类对应的 java.lang.Class 对象没有任何引用，也无法通过反射访问到这个类。

不过条件太严苛了，类卸载很少实际发生，所以大多数情况下静态成员变量会一直活到程序运行结束。

## 方法-基础知识

### 方法的存储

方法与变量完全不同，方法不是用来存储数据的，而是用来执行的，因此不能按照变量的方式存储方法。不然，对于不同的对象来说成员变量的值是不同的，然而成员方法却永远是一样的，难道每new一个新对象，都要把方法重新存一遍吗？这显然不合理。

前面应该提到过，对象的存储分为`对象名称`、`对象结构`和`对象数据`三个部分，其中`对象结构`其实也就是`类的结构`，其中就包含了方法的名称、参数、返回值实现等信息，所以方法是存在`元空间`的。

如果这个方法所属的类被类加载器加载，那么连同方法的字节码会整个存在到`元空间`内。如果没有被加载，那就不用放到元空间，这就是 Java 等`懒加载`。


### 方法的执行

在`元空间`内存储的是方法的静态特征，`元空间`是独立且只读的，真正执行方法自然是需要放到 JVM 自己管理的空间内——也就是`栈`。 

如果是一般的解释器，肯定会根据方法的字节码，拿一句指令，就把指令 push 到栈内，然后再送给 CPU 执行，然后拿下一句，继续执行......最后方法的指令拿取完毕后，就是方法的完成之时，这个时候栈内的方法全部 pop。

然而，如果沿用以上方式，肯定会执行地特别慢，JVM 有着 JIT 的加持，画风早不是这样了。JIT 方式确实会在字节码运行的前期一句一句解释，然而若这段字节码调用的次数太多（比如C1 编译器默认阈值通常是 1500 次，C2 编译器默认是 10000 次），JVM 就会判定其为`热点方法`，JIT 会在下一次解释的时候，一边解释一边缓存一个`直接操控CPU、寄存器和内存`的机器码，在这之后调用这个方法就不必再解释运行了，而是直接让 CPU 接管方法的机器码，`效率直接起飞`。


### 静态方法

#### 静态方法的存储

静态方法也是存在`元空间`的，这一点和非静态方法是一致的，因为都是要方便所有对象共享一个方法。

不过虽说静态方法和非静态方法都存在`元空间`，但是其存在形式上完全不同的，其调用方式也完全不同。

> 方法的静态与否在执行上有什么本质区别？

最大的区别就是：`this指针`。

非静态方法是由对象本身调用的，而对于这个对象而言，对象的成员方法是完全知晓自身的成员变量数据的，也有要随时调用这些数据的需求，因此：`非静态方法自带上下文`。其表现为，编译器`javac`在将方法编译时，会在其传入参数表内擅自添加一个`this`到第一位，用以给方法提供查询对象上下文的能力。

而静态方法则简单粗暴，完全不需要任何查询上下文，所以也就不需要`this`，`javac`也不需要添加参数。

所以，调用静态方法时，最好使用类名调用而非对象名，这样对于代码 reader 而言不容易造成混淆。

#### 静态方法为什么只能调用静态变量

和上面的静态变量的原因类似，静态方法由于时类被加载时就被存入元空间，在未实例化对象前静态方法就存入内存了，此时的静态方法是可以调用的。不过，显然理论上不可能出现静态方法调用非静态变量的情况，因为对象都不存在，哪来的非静态变量？

所以，本着有风险就要避免，Java 官方干脆一刀切地禁止了静态方法调用非静态变量这种可能产生异常的做法。

> 那么，非静态方法怎么调用非静态变量的？

原因在于非静态方法默认持有的`this`参数，这样出在`元空间`内的方法字节码，才能知道自己现在是被哪个对象调用，需要读取哪个对象的变量。

事实上，`this`指针的缺失就是本质原因，假如手动传入`this`，那么静态方法也可以调用非静态成员变量，例如

```java
public class Obj{
    public Type ele;
    public static void print(Obj obj, Type newEle){
        obj.ele = newEle;
    }
}
```

## 面向对象（OOP） VS 面向过程（POP）

性能上，OOP普遍打不过POP，主要有以下几个原因：

- Cache命中率：POP 的执行策略，通常将数据置于连续内存中，因此访问数据时更容易将相关性高的数据放入Cache；而 OOP 的数据则存在各个对象中，而对象的地址随机分布在内存中，而且伴随着 GC 的垃圾回收机制，对象的内存地址更容易变动，Cache 命中率只能用灾难形容。

- 内存占用：OOP 内存消耗更高，因为要为对象本身的组织分配内存，GC 的耗时更高，寻址的成本也越高。

- 预测失效：由于 OOP 存在多态，对象调用方法时没有办法保证调用的谁的方法，有可能是自己的，也有可能是子类对象的，即`引用类型变量发出的方法调用的到底是哪个类中的方法，必须在程序运行期间才能确定`，总之就是无法完美预测，还得到堆区看对象的虚函数表才能确定，又是一次性能浪费；而 POP 在编译阶段就已经把跳转地址写好了，完全不需要即时预测。

## 接口 & 抽象类

|  | 接口 | 抽象类 |
|---------|------------|-----------|
| 目的 | 表示拥有功能 | 表示属于某个类 |
| 继承&实现 | 可多继承其他接口 | 只能单继承（与非抽象类一致） |
| 成员变量 | 必须是public static final且必须赋初值 | 任意（与非抽象类一致） |
| 方法 | 1.可以用default给定默认实现；2.static方法不可重写，且必须直接实现 | 1.可以定义抽象方法和非抽象方法；2.抽象方法必须在子类实现 |

> Java8 引入了接口的 default 方法。

```java
public interface I{
    default void func(){
        //···;
    }
}
public class Impl_1 implements I{
    @override
    public void func(){
        //···
    }
}
public class Imple_2 implements I{
}

```

default 方法可以不用重写，实际上也很少去重新，因为 default 方法可以不在修改类实现的情况下也`拓展`类的方法。

> Java8 引入了接口的 static 方法。

```java
public interface I {
    public static void func(){
        //···
    }
}
public class Impl implements I{
    //···
}
psvm(){
    new Impl().func();  //非法
    I.func();   //合法
}
```

和类的 static 成员方法一样，可以使用接口名称调用，但是更加激进的是官方只允许使用接口调用，而不允许使用接口实现类的对象调用。

> Java9 引入了接口的 private 方法

主要是和类的成员方法一致，只能让接口内部的方法访问，而不能直接被外部访问。

## 拷贝

### 浅拷贝 & 深拷贝

最大的区别来自于对象中的`对象成员`的拷贝策略。浅拷贝中针对`对象成员`的策略，是只新建一个引用，引用的地址仍然指向原有对象的对象成员，相当于拷贝的只有引用本身；而深拷贝则会`以对象成员为蓝本，new一个新对象作为对象成员`，除了引用本身会拷贝，对象成员也要分配新的空间并拷贝。

`Person p = new Person();`，假设这是一个对象的`数据`存储结构（注意区分结构和引用）：

```
地址：0x66452820
类型：Person
名称：p
成员变量0：  
    类型：String
    引用名称：name
        （该引用在栈区的地址：0x777352862）
        引用的地址：0x3338572
        这个地址上的值："Steve"
成员变量1：
    类型：int
    名称：age
    数值：18
```

### 浅拷贝

关于浅拷贝，Java官方给出过规范：必须在类中实现`Cloneable`接口的`clone()`方法，而实现方法就是使用`Object`类的浅拷贝方法`clone()`：

```java
public class Person implements Cloneable{
    String name;
    int age;

    @override
    public Person clone(){
        return (Person) super.clone();
    }
}
```

调用`Person p1 = p0.clone();`，浅拷贝一个p1，得到的新对象内部存储：

```
地址：0x43211556
类型：Person
名称：p1
成员变量0：  
    类型：String
    引用名称：name
        （该引用在栈区的地址：0x288367347） 
        引用的地址：0x3338572
        这个地址上的值："Steve"
成员变量1：
    类型：int
    名称：age
    数值：18
```

可以看到，对象内部的对象成员`name`确实是一个由新的引用链接，因为引用本身的地址变化了；然而引用指向的地址却没有变化，指向的仍然是被拷贝对象的对象成员地址。

### 深拷贝

Java官方没有提供深拷贝的方法，如果需要的话得自行实现。可以试试重写clone方法：

```java
public class Person implements Cloneable{
    String name;
    int age;

    @override
    public Person clone(){
        Person finale = new Person();
        finale.age = this.age;
        finale.name = this.name;
        return finale;
    }
}
```

然而，如果对象成员里面还有对象成员，这么重写就太麻烦了，而且现在也`不建议手动重新clone()方法`。可以用拷贝构造方法：

```java
public class Person{
    String name;
    int age;

    public Person(Person p){

    }
}
```

不过，还有更简单的方法，调用各家厂商实现的`Json转Object对象`，就不用担心地址不是最新的了，因为Json完全不包含地址信息，转的时候一定会重新分配。

### 基本类型包装类的拷贝问题

首先一句话，包装类的对象直接用等号赋值，`既是浅拷贝也是深拷贝`，虽然我们主观上是想浅拷贝，但在客观上也实现了深拷贝，原因在于基本类型的包装类的对象是`不变对象`，其包装类中的基本类型成员变量是`final`的。

我们回想一下，为什么要进行深拷贝？是不是为了防止浅拷贝中两个对象的对象成员指向`同一个地址`，在赋值、修改时发生连锁干扰？而包装类在赋值、修改时，由于那个地址所在的值是写死的，于是只能另外找个地址存改后的数据（或者找到已经是这个值的地址），然后把这个地址的引用返回去，原先的地址的那个值完全不受干扰，这不就避免了浅拷贝的干扰吗？

所以曲线救国，四舍五入，回归性原理：浅拷贝就是深拷贝

## String 基础

### String 对象的不可变性

与几个包装类一样，内部的基本类型成员变量是用`final`修饰的，肯定不可变。

### 字符串常量池

主要是为了优化大量使用 String 时的系统性能，创建一个 String 对象，对象内存的`final byte[]`会被存入`字符串常量池`（Java8后在`堆区`），作为一个完整的 String 类型对象。若再创建一个相同值的字符串，则直接将地址返回引用，这样就防止大量分配冗余空间。

```java
//常量池：无

String a = "ab";
//常量池：  "ab"    0x00026531190
//a指向的地址：      0x00026531190

String b = "ab";
//常量池内有“ab”，那就直接返回地址给引用
//b指向的地址：      0x00026531190
```
>String的创建和修改为什么只建议用等号而非new ？

因为 String 对象时线程安全的，我们所害怕的情况：两个代码段共享同一个地址，导致线程不安全，这种情况在 String 中时不存在的，因为 String 不管是再赋值还是拼接等，原有对象永远不会受干扰。

那`new`呢？这个关键字强制要求 JVM 在堆区分配空间然后`新建一个String对象`，这实际上是造成浪费的。

所以，建议使用等号而非new。

### String 的常量折叠

String 的常量直接拼接时，JVM会直接将这个表达式优化成表达后的常量：

```java
String a = "string";
String b = "str" + "ing";
```

这个式子中，由于b是两个字符串常量间的相加式拼接，JVM 在编译成字节码的时候`顺手`就把它直接优化成：`String b = "string";`了，那么在真正运行的时候，前面a的存在表明常量池中一定已经有了相同值的字符串，所以b和a共享同一个引用。

不过，如果常量池里面没有，那常量折叠后的字符串就放到常量池里面，等待复用。

> 那么如果是引用之间的相加拼接呢？

首先要知道，编译器为什么可以对常量进行折叠，对引用就不能折叠？本质原因是：常量是`JVM可以一眼看出来`，引用不行，所以一般情况下引用就没法折叠。

然而也有例外，引用使用`final`修饰，那么JVM就看懂了，然后就可以折叠了。

### String 引用之间的拼接

字符串引用间、或者常量与引用间使用`+`拼接。

Java8及以前的底层是调用了`StringBuilder`的`append()`方法。每次使用`+`都会`new`一个`StringBuilder`对象调用`append()`，连续的+也就是连续地调用append()方法。这种在循环中特别容易造成性能浪费，因为会疯狂地创建对象：

```java
String a;
s.forEach(str=>{
    a += str;
});
```

而在Java9之后，由于弃用了 StringBuilder，所以底层并非调用 append 了，取而代之的则是使用一条字节码指令`invokedynamic`。这条指令是在`程序运行期间`的，执行者是JVM。而在Java8以前，在`编译期间`直接替换字节码。

首先，真正执行拼接前，JVM会检查一下表达式中要拼接的全部字符串的长度，算出拼接后要多少空间；然后去`堆区`申请等长的空间，再把拼接的字符串直接依次放进去；最后再将字符串组织成一个对象，返回它的引用。

> 然而，使用字节码指令拼接的字符串，不会遵照之前的字符串创建，即放到常量池，为什么？

这是JVM的内存保护策略，即：任何在`执行阶段`拼接的字符串，不会放到常量池复用。

重点是`执行阶段`。我们回想一下常量折叠，这是发生在`编译阶段`的，javac编译结束后，字节码内，原先的常量加法拼接的表达式直接就被转换成了拼接后的字符串常量，因此执行阶段拿到的只会是一个字符串常量，JVM不会知道这个常量最开始是一个表达式。

然而执行阶段，包括字节码指令`invokedynamic`，也包括上面提到的`append()`方法，这些拼接后的结果都不会放到常量池，不然在实际生产运营业务中会大量产生字符串拼接，大量访问率低甚至不会二次访问的字符串，如果都放到常量池的话性能直接爆炸。

> intern() 方法又做了什么？

上面提到，任何在`执行阶段`拼接的字符串，不会放到常量池复用，而使用`intern()`可以`显式地`让JVM把执行阶段拼接的字符串也加入常量池。例如：

```java
String s = (a+b+c+d).intern();
```

那么此时，JVM先是在`堆区`内私下里把abcd拼好，然后去常量池问有没有这个字符串，有的话就返回常量池里的对象，堆区里那个拼好的字符串删了；没有的话，就把拼好的字符串放到常量池，然后返回这个对象的引用。

## 反射 基础

### 什么是反射

JVM 可以在运行时动态地拿到类的详细信息，这允许在运行时才确认类的信息。


### 谁在用反射

首先，我们人肯定用得很少，或者说基本不用。用这个的多是一些支持自动化的组件，比如 Spring 和 Mybatis 这些框架。

### 从内存的角度说反射

#### 反射的物理层基础

当 ClassLoader 加载一个类（注意是字节码）时，首先会把类的一些固有信息，例如类名、有哪些成员、成员方法的实现段、静态成员等，都会存到`元空间`，其格式是用`Cpp`写的，但是注意，只是存储格式是 Cpp 的，其成员名称、方法代码段原文是以 .class 存储的。

在将类的固有信息存入`元空间`之后，紧接着 JVM 会实例化一个`java.lang.Class`类型的对象存在`堆区`，这个对象同样用来存储类的固有信息，但和`元空间`的那个 Cpp 结构体的区别在于：`元空间`里那个存的是`真正的数据`；`java.lang.Class`对象存的是`指向元空间那片空间的Cpp指针`，所以这个 Class 对象相当于一个`代理`。

方法也是一样的，方法的实现段存在`元空间`，`java.lang.reflect.Method`对象就存方法在`元空间`内真实存在的方法实现段的 Cpp 指针。

#### 元空间内方法实现段的存储

首先，Java 代码被翻译成字节码被存入元空间，这里的字节码并非一整段字符串，而是按照一句一句存储的`数组`，就比如下面的 java 代码：

```java
public void run(){int a = 1;}
```

这个方法的实现段`int a = 1;`被翻译成字节码就是：

```class
iconst_1
istore_1
return
```

那在`元空间`内是怎么存这个方法的？（并非实际存储，只是模拟）

```
0x000000    iconst_1    <--- ConstMethod* _constMethod
0x000016    istore_1
0x000032    return
```

被实例化的 Method 对象内存在的方法指针`ConstMethod* _constMethod;`就是`0x000000`，代表这个代码段的字节码一句一句，存放在这个地址。

#### 反射怎么执行方法？

当需要用反射的时候，可通过`java.lang.reflect.Method`对象调用`invoke(args)`方法，这一步可以是由我们自行编写代码发起的，也可以是各种框架内部写死的调用方法发起的。而这个方法在底层，实则是 JVM 主动调用了一个 由 Cpp 实现的 `native方法`，由该方法执行。`native方法`再到`元空间`内，根据方法的指针，查找到代码段的字节码，然后一句一句解释执行。

不过，考虑到反射方法执行的极高开销（jvm 调用`native方法`，运行时动态路由到方法地址），反射方法和普通方法类似，当成为热点方法后，JVM 会用字节码动态地拼凑出一个全新的类，用来直接调用这个方法，然后通过类加载器`加载`到内存中（当然，这个方法的实现段一样存在`元空间`）。之后的调用就简单了，JVM 不需要再调用底层 Cpp 代码动态路由方法地址，而是和普通方法一样处理，JVM 通过访问虚函数表，`直接定位`到方法的实现段，并加载到`栈区`解释执行。当然，如果实在太热，也会在超过调用次数阈值后，直接缓存为机器码，让 CPU 直接执行。 

#### 反射性能为什么不好？

从上面反射的执行就可以看出，反射方法之所以性能不如普通方法，已然有以下两大原因：

- JVM 调用底层 Cpp 代码耗费性能；

- Cpp 代码需要在 JVM 运行时，通过不断地路由才能确定方法的地址。

然而，即便反射方法在经过16次后，也即克服了上面两大问题，反射方法的性能会依然不如普通方法，这里还有三大原因：

- `invoke(Object ...)` 方法的参数为可变参数，可变参数的处理相当麻烦，加重性能负担；

- 方法权限问题：反射执行方法在编译时不会检查权限，因为反射是在 JVM 运行时才进行的，也就是说被 invoke 的方法有可能不是 public 的，而 private 方法原则上是不能被其他对象调用的，正因为有这种可能性，执行时底层会不断地问询鉴权是否有权执行这个方法，这又是性能负担。不过，可以使用`method.setAccessible(true);`，强制让反射方法获取权限，并且跳过鉴权的环节；

- 无法内联：`inline`是优化执行效率的方法，普通方法内直接把方法代码段粘贴到调用的地方避免跳转地址的开销，然而反射方法做不到精确的预测，内联大概率失败，所以无法吃到这个 buff，性能自然就下来了。

### 场景

- 动态代理。

- 注解：需要利用反射读取注解对应的类、方法，才能知道这个注解是什么意思。

- IoC & DI：基于动态代理和注解。

- ORM 关系对象映射，通过获取类名拼接关键字和 sql ，从而自动化数据库操作。

## 代理

### 什么是代理

代理就是让中间人执行一件事，比方说有一个方法

```java
public class CLAZZ{
    public void func(){
        //...;
    }
}

```

我们给他找一个代理方法：

```java
public class Proxy{
    public void proxyFunc(CLAZZ clazz){
        clazz.func();
    }
}
```

在代理方法里面，执行了被代理方法，这就是最简单的代理关系。

而我们在代理中最重要的目的就是：`增强`方法的功能，比如让`func()`每次执行都给个日志，但是不能修改方法本身，该怎么做？在代理里面实现：

```java
public void proxyFunc(CLAZZ clazz){
    System.out.println("log: func() working...");
    clazz.func();
}
```

### 静态代理

然而，如果有10000个方法都要经过代理，难道也要手写10000个代理方法吗？显然不可能。上面的方式就是`静态代理`。

我们不禁思考：假如我要让不同方法输出同样格式的日志，难道就只能针对每个不同的方法，写各自对应但是极为相似的代理方法吗？

### 动态代理

`动态代理`可以解决这个问题，动态代理可以

而目前常见的有两种动态代理方法：JDK 和 CGLIB 方式。

### JDK 代理

#### 使用方法

JDK 代理方式要求使用`接口+实现类`，其核心是代理类必须实现`InvocationHandler`接口。

我们假设要为不同的方法，打上相同的输出日志格式，假设有如下定义：

```java 
//接口
public interface Service{
    void func();
}

//方法实现类
public class ServiceImpl implements Service{
    void func(){
        //······实现
    }
}
```

我们使用

```java
//代理类
class Handler implements InvocationHandler {
    // 持有被代理对象
    private Object target; 

    //构造
    public Proxy(Object target) { 
        this.target = target; 
    }

    /**
     * Method method： 实际被代理的方法的对象
     * Object[] args： 传入的method被代理方法的参数
     */
    @Override
    public Object invoke(Object proxy, Method method, Object[] args)throws Throwable {
        System.out.println("【前置增强】记录日志");
        Object result = method.invoke(target, args); // 反射调用原方法
        return result;
    }
}
```

主方法内调用：

```java
//被代理对象
Service target = new ServiceImpl();
//代理类，传入被代理对象
InvocationHandler handler = new Handler(target);
//构造代理对象
Service proxy = (Service) Proxy.newProxyInstance(
    target.getClass().getClassLoader()
    , target.getClass().getInterfaces()
    , handler
);
//调用
proxy.func();
```

这样就可以使用代理类调用增强后的方法了。

#### proxy 代理对象

代理对象 proxy 直接来源于`Proxy.newProxyInstance`，该方法的三个参数分别为：该类的类加载器、被该类实现的所有接口、某个实现了 InvocationHandler 的类的对象。

当使用 proxy 调用了被代理方法时，会将方法转发给实现了 InvocationHandler 的类的对象，即 handler， handler 随后调用 invoke 方法，实现`func()`方法的增强。

> 为啥需要传入类加载器？

JDK 代理的本质是让 JVM 实时创建一个被代理类的`接口实现类`，创建类后就必须加载到内存中，传入的类加载器就是起这个作用的。

至于为什么传入的是被代理类的类加载器，是为了安全和惯例。

> 为啥需要传入实现的接口？

JDK 代理的本质是让 JVM 实时创建一个被代理类的`接口实现类`（这也是为什么必须要是接口+实现类的形式），这个创建类必须可以`完全取代被代理类`，所以被代理类实现的接口必须也被创建类实现，否则在语法上也说不通，传入实现的接口也是为了得知被代理类实现类哪些接口。

#### invoke

可以看到 handler 内部，`invoke`方法传入了三个参数：动态生成的代理类、被调用的方法、方法的参数。
